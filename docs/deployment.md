# Развёртывание Attendance

## Конфигурация среды

`python ops/init_env.py` генерирует ключи и пароли в локальном `.env`. Файл исключён из Git и контекста сборки. `AUTH_KEY` подписывает JWT, `QR_KEY` подписывает QR-коды, `POSTGRES_PASSWORD` используется прикладной ролью, `POSTGRES_ADMIN_PASSWORD` используется администратором PostgreSQL. `DEMO_PASSWORD` применяется только командой `seed`. Для каждой среды создаются отдельные ключи, пароли и тома.

Docker Compose запускает PostgreSQL, отдельную миграцию, FastAPI и Caddy. PostgreSQL и FastAPI доступны внутри Docker-сети. Caddy принимает HTTPS и передаёт статику и REST API с одного адреса. `/healthz` проверяет доступность HTTP, `/readyz` проверяет подключение к PostgreSQL и наличие схемы. Логи исключают тела запросов, JWT и координаты.

## Локальный HTTPS

По умолчанию стенд слушает адрес `127.0.0.1` и выставляет Caddy на 80 и 443. Caddy выпускает сертификат `localhost` через свой локальный центр сертификации. Получите публичный корневой сертификат для проверки соединения.

```sh
docker compose cp caddy:/data/caddy/pki/authorities/local/root.crt attendance-local.crt
curl --cacert attendance-local.crt https://localhost/readyz
```

После проверки отпечатка этого файла его можно импортировать в доверенные сертификаты текущего пользователя или клиента. При занятых портах задайте `HTTPS_PORT` и `HTTP_PORT` в `.env`. При параллельном запуске отдельного стенда задайте имя Compose-проекта, порты и свободные `PROXY_SUBNET`, `PROXY_IP_RANGE`, `PROXY_ADDRESS`. Адрес Caddy должен входить в подсеть и лежать вне диапазона динамических адресов.

## Доступ с телефона

Для размещения на сервере укажите домен в `ATTENDANCE_HOST`, задайте `BIND_ADDRESS=0.0.0.0` и направьте DNS-запись на сервер. Caddy получит публичный сертификат при доступных 80 и 443. Запускайте загрузку `seed` только в изолированной учебной среде. Опубликованный образ можно развернуть через `ATTENDANCE_IMAGE=ghcr.io/arssedot/attendance-control-system:<тег>` и `docker compose up --no-build -d --wait` после `docker compose pull app`.

QR-ссылка использует HTTPS-адрес, с которого преподаватель открыл кабинет. Этот адрес должен быть доступен с телефона. Если внешний адрес отличается, задайте его явно через `PUBLIC_BASE_URL`, например `https://attendance.example.org`. Адрес `localhost` в QR подходит для проверки с того же компьютера или с эмулятора, подключённого через ADB.

Установите зависимости через `npm ci`. Скопируйте `clients/mobile/.env.example` в `clients/mobile/.env` и задайте `EXPO_PUBLIC_API_URL` равным HTTPS-адресу сервера. Переменная входит в клиентскую сборку и предназначена для публичного адреса. Команды запуска генерируют системные проекты из конфигурации Expo.

```sh
npm run android --workspace @attendance/mobile
npm run ios --workspace @attendance/mobile
```

Для Android нужны Android SDK и JDK, для iOS — macOS и Xcode. Совместимые версии SDK описаны в документации [Expo SDK 58](https://expo.dev/changelog/sdk-58). Для проверки сборки JS выполните `npm run export --workspace @attendance/mobile`.

Для Android-сборки на Windows используйте короткий путь к рабочей копии, если Ninja сообщает об ограничении длины пути. Expo-конфигурация задаёт предел для путей объектных файлов CMake, чтобы CMake автоматически сокращал длинные имена.

В Android-эмуляторе доступ к локальному серверу можно проверить через `adb reverse tcp:443 tcp:443`. Перед `expo prebuild --platform android` укажите `ATTENDANCE_ANDROID_DEBUG_CA` как абсолютный путь к корневому сертификату Caddy и `EXPO_PUBLIC_API_URL=https://localhost`. Сгенерированное правило доверия действует для `localhost` в Android debug-сборке.

## Резервная копия и восстановление

```sh
python ops/backup.py create
python ops/backup.py verify backups/attendance-<дата>-<идентификатор>.dump
```

Команда `verify` создаёт отдельную базу с именем `attendance_restore_…`, восстанавливает схему и данные и выводит количество строк и первичных ключей таблицы отметок. Сверьте результат с контрольной точкой выпуска. Резервные копии содержат сохранённые координаты геоотметок. Ограничьте доступ к файлам и храните их отдельно от сервера с соответствующим сроком хранения.

Перед обновлением сохраните резервную копию и тег или digest работающего образа. После обновления проверьте `/readyz`, вход и основные сценарии. Для отката совместимой схемы верните предыдущий образ. Если схема изменилась несовместимо, остановите приложение, восстановите проверенный снимок в отдельной БД, затем переключите конфигурацию на восстановленную базу. Обратный скрипт первой миграции удаляет таблицы и их данные.

## GitHub Actions

Workflow проверяет API на отдельной PostgreSQL, компилирует клиенты, запускает браузерный сценарий и проверяет восстановление. Успешные сборки `main` и тегов `v*` публикуются в GHCR по SHA коммита и по имени ветки или тега. Для публикации применяется встроенный `GITHUB_TOKEN`. Секреты хоста и БД остаются в среде развёртывания.
